## نصب و راه‌اندازی

```bash
# ۱. نصب وابستگی‌ها
npm install

# ۲. ساخت فایل تنظیمات
cp .env.example .env
# سپس مقادیر داخل .env را پر کنید (بخش بعد)

# ۳. ساخت جداول دیتابیس و داده‌های اولیه
npm run setup

# ۴. اجرای پنل
npm run dev
```

سپس به `http://localhost:3000/register` بروید.
**اولین حسابی که ثبت‌نام می‌کند به صورت خودکار مدیر کل می‌شود.**

پس از ثبت‌نام:

1. به `/admin/catalog` بروید و روی «همگام‌سازی با هتزنر» بزنید.
2. به `/admin/pricing` بروید و نرخ یورو و درصد سود را تنظیم کنید.
3. به `/admin/settings` بروید و اطلاعات برند و درگاه را کامل کنید.

## پیکربندی محیط

مقادیر حیاتی فایل `.env`:

### کلیدهای امنیتی

```bash
# کلید امضای نشست‌ها
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"

# کلید رمزنگاری رمز روت سرورها (دقیقاً ۶۴ کاراکتر هگز)
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

> **هشدار:** پس از راه‌اندازی، `ENCRYPTION_KEY` را هرگز تغییر ندهید. با تغییر آن، رمز روت تمام سرورهای موجود غیرقابل بازیابی می‌شود.

### توکن هتزنر

از کنسول هتزنر: `Project → Security → API Tokens → Generate API Token` با دسترسی **Read & Write**.

توکن‌ها در فایل `.env` نگهداری نمی‌شوند؛ آن‌ها را از پنل، در بخش **حساب‌های هتزنر**
(`/admin/hetzner`) اضافه کنید تا رمزنگاری‌شده در دیتابیس ذخیره شوند و بتوانید هر تعداد
حساب که خواستید داشته باشید. اگر از نسخه‌های قدیمی‌تر می‌آیید و هنوز مقدار
`HETZNER_API_TOKEN` در `.env` دارید، ورکر آن را یک بار به عنوان نخستین حساب وارد
می‌کند و پس از آن می‌توانید از `.env` حذفش کنید.

### درگاه زیبال

مقدار پیش‌فرض `ZIBAL_MERCHANT=zibal` یعنی حالت تست و پول واقعی جابه‌جا نمی‌شود.
کد مرچنت واقعی خود را جایگزین کنید.

آدرس بازگشت که باید در پنل زیبال ثبت شود:

```
https://YOUR-DOMAIN/api/wallet/callback
```

### ایمیل و پیامک

اختیاری‌اند ولی به‌شدت توصیه می‌شوند: بدون SMTP، تایید ایمیل و اطلاع‌رسانی‌های مهم (اتمام موجودی، تعلیق سرور) ارسال نمی‌شود.

## استقرار روی سرور

> **روش پیشنهادی: داکر.** فایل‌های `Dockerfile` و `docker-compose.yml` آماده‌اند و راهنمای
> گام‌به‌گام از صفر — نصب داکر، دیتابیس، Nginx، گواهی TLS، سرویس آزمایش ایران و
> به‌روزرسانی — در [docs/نصب-روی-سرور.md](docs/نصب-روی-سرور.md) است. روش PM2 پایین
> برای کسانی است که داکر نمی‌خواهند.

### ۱. بیلد

```bash
npm ci
npm run build
npx prisma migrate deploy   # یا npm run db:push در نصب اولیه
npm run db:seed
```

### ۲. اجرا با PM2

```bash
npm install -g pm2

pm2 start "npm run start" --name pasargad-app
pm2 start "npm run worker" --name pasargad-worker

pm2 save
pm2 startup
```

> **مهم:** فقط **یک نمونه** از ورکر باید اجرا شود. اجرای چند نمونه باعث کسر چندباره هزینه می‌شود. سیستم قفل دیتابیس دارد ولی به آن اتکا نکنید.

### ۳. Nginx

```nginx
server {
    listen 443 ssl http2;
    server_name panel.example.com;

    ssl_certificate     /etc/letsencrypt/live/panel.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/panel.example.com/privkey.pem;

    client_max_body_size 10m;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_cache_bypass $http_upgrade;
    }
}
```

پس از تنظیم دامنه، مقدار `APP_URL` در `.env` را به آدرس نهایی تغییر دهید؛ این آدرس در لینک‌های ایمیل و بازگشت از درگاه استفاده می‌شود.

### ۴. جایگزین ورکر (اگر امکان اجرای پروسه دائمی ندارید)

مسیر `/api/cron` همان کارها را از طریق HTTP اجرا می‌کند:

```bash
# در crontab سرور
5  * * * * curl -s -H "Authorization: Bearer $CRON_SECRET" "https://panel.example.com/api/cron?job=hourly-billing"
10 * * * * curl -s -H "Authorization: Bearer $CRON_SECRET" "https://panel.example.com/api/cron?job=monthly-billing"
*/2 * * * * curl -s -H "Authorization: Bearer $CRON_SECRET" "https://panel.example.com/api/cron?job=finalize-provisioning"
*/10 * * * * curl -s -H "Authorization: Bearer $CRON_SECRET" "https://panel.example.com/api/cron?job=sync-servers"
0  3 * * * curl -s -H "Authorization: Bearer $CRON_SECRET" "https://panel.example.com/api/cron?job=cleanup-suspended"
45 3 * * * curl -s -H "Authorization: Bearer $CRON_SECRET" "https://panel.example.com/api/cron?job=sync-catalog"
```

## چند حساب هتزنر و ظرفیت

هر پروژه Hetzner Cloud سقف مستقلی برای تعداد سرور دارد (پیش‌فرض ۱۰ عدد). برای فروش در
مقیاس بزرگ‌تر، پنل هر تعداد حساب را کنار هم می‌چیند و ظرفیت آن‌ها را روی هم حساب می‌کند.

### افزودن حساب

در `/admin/hetzner` روی **افزودن حساب** بزنید و این مقادیر را وارد کنید:

| فیلد | معنی |
| --- | --- |
| نام حساب | برچسب دلخواه برای شناسایی، مثلاً «هتزنر اصلی» |
| توکن API | توکن Read & Write؛ با AES-256-GCM رمز و ذخیره می‌شود و دیگر نمایش داده نمی‌شود |
| سقف تعداد سرور | سقف پروژه در هتزنر |
| اولویت | عدد کوچک‌تر زودتر امتحان می‌شود |

دکمه **آزمایش** پیش از ثبت، اتصال را بررسی می‌کند و تعداد سرورها و لوکیشن‌های آن حساب را
نشان می‌دهد.

### انتخاب حساب هنگام ساخت سرور

1. حساب‌های فعال به ترتیب اولویت مرتب می‌شوند؛ حساب‌هایی که ظرفیتشان پر است یا وضعیت خطا
   دارند کنار گذاشته می‌شوند.
2. کلیدهای SSH کاربر روی حساب انتخاب‌شده آپلود می‌شوند (اگر از قبل نباشند).
3. اگر هتزنر خطای `resource_limit_exceeded` بدهد، همان لحظه سقف واقعی آن حساب یاد گرفته
   و ذخیره می‌شود، به تیم اطلاع می‌رسد و ساخت روی حساب بعدی ادامه پیدا می‌کند.
4. اگر توکن نامعتبر یا فقط‌خواندنی باشد، حساب به وضعیت خطا می‌رود و از چرخه خارج می‌شود.
5. اگر هیچ حسابی جواب ندهد، هزینه کسرشده کامل به کیف پول کاربر برمی‌گردد و خطای
   «ظرفیت ساخت سرور تکمیل است» با کد ۵۰۳ برگردانده می‌شود.

هر سرور به همان حسابی که رویش ساخته شده گره می‌خورد؛ تمام عملیات بعدی (روشن و خاموش،
اسنپ‌شات، فایروال، کنسول، تعویض آی‌پی) با توکن همان حساب انجام می‌شود.

### دیدن ظرفیت

خلاصه ظرفیت هم بالای `/admin/settings` و هم در `/admin/hetzner` دیده می‌شود: مجموع سقف،
تعداد مصرف‌شده، جای خالی و درصد اشغال. هر حساب نوار ظرفیت جداگانه دارد و با رسیدن به
۸۰٪ هشدار و در ۱۰۰٪ اخطار قرمز نمایش داده می‌شود.

ورکر هر ساعت ظرفیت همه حساب‌ها را از هتزنر تازه می‌کند؛ دکمه **به‌روزرسانی ظرفیت** هم
همین کار را دستی انجام می‌دهد.

### غیرفعال کردن یا حذف حساب

با خاموش کردن کلید «استفاده برای ساخت سرور جدید»، سرورهای فعلی آن حساب دست‌نخورده
می‌مانند اما سرور تازه‌ای رویش ساخته نمی‌شود — مناسب زمانی که می‌خواهید حسابی را به آرامی
از رده خارج کنید. حذف حساب فقط توکن را از پنل پاک می‌کند؛ سرورهای هتزنر باقی می‌مانند و
پنل دیگر نمی‌تواند آن‌ها را مدیریت کند.

## آدرس مسدود و بررسی دسترسی از ایران

هتزنر هنگام ساخت سرور یک IPv4 تصادفی می‌دهد و بخشی از رنج‌هایش از قبل در ایران مسدود است.
بدون چاره‌اندیشی، مشتری پول می‌دهد و سروری تحویل می‌گیرد که به آن دسترسی ندارد. پنل این
مشکل را در سه لایه حل می‌کند.

### لایه ۱ — آزمایش پیش از تحویل

تنها راه قابل اعتماد برای فهمیدن اینکه یک آدرس از ایران باز است، وصل شدن از داخل ایران
است. چون پنل معمولاً روی سرور خارج اجرا می‌شود، این کار به یک سرویس کوچک سپرده شده که
روی یکی از سرورهای ایرانی خودتان اجرا می‌شود.

راه‌اندازی سرویس روی سرور ایرانی:

```bash
# ۱. یک کلید تصادفی بسازید
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

# ۲. فایل را روی سرور ایرانی بگذارید و اجرا کنید
IRAN_PROBE_SECRET=کلیدی-که-ساختید PORT=8787 node iran-probe-agent.mjs

# یا با pm2 برای اجرای دائمی
pm2 start iran-probe-agent.mjs --name iran-probe
pm2 save
```

سپس در فایل `.env` پنل:

```bash
IRAN_PROBE_URL=https://probe.yourdomain.ir
IRAN_PROBE_SECRET=همان-کلید
```

> سرویس را پشت Nginx با TLS بگذارید و در فایروال فقط آی‌پی سرور پنل را مجاز کنید.
> این سرویس هیچ داده‌ای ذخیره نمی‌کند و آدرس‌های خصوصی را هم رد می‌کند تا به پروکسی
> داخلی تبدیل نشود.

روند کار پس از ساخت هر سرور:

1. پنل صبر می‌کند تا هتزنر بگوید سرور روشن است و نود ثانیه هم به سیستم‌عامل فرصت بوت
   شدن می‌دهد.
2. سرویس ایرانی به پورت ۲۲ آن آدرس وصل می‌شود.
3. همزمان چند آدرس از سرورهای سالم خودمان هم آزمایش می‌شود تا مرجع مقایسه باشد.
4. نتیجه‌گیری:

| مقصد | مرجع‌ها | نتیجه |
| --- | --- | --- |
| جواب داد | — | آدرس سالم است |
| جواب نداد | جواب دادند | آدرس مسدود است |
| جواب نداد | جواب ندادند | نامشخص؛ دور بعد دوباره |
| — | سرویس ایرانی اینترنت نداشت | نامشخص؛ دور بعد دوباره |

5. اگر آدرس مسدود تشخیص داده شود، پنل خودش و **بدون هیچ هزینه‌ای** آدرس تازه می‌گیرد و
   آن را هم آزمایش می‌کند. سقف این تعویض خودکار در تنظیمات تعیین می‌شود.

نکته مهم: تا وقتی هیچ سرور تاییدشده‌ای وجود نداشته باشد، مرجعی برای مقایسه نیست و پنل
هیچ‌وقت به تنهایی حکم «مسدود» نمی‌دهد. این عمدی است و جلوی تعویض بی‌دلیل آدرس سرورهایی
را می‌گیرد که فقط کند بوت شده‌اند.

### لایه ۲ — حافظه رنج‌های سوخته

فیلترینگ معمولاً یک بلوک /24 کامل را می‌بندد، نه یک آدرس تنها. پس هر مشاهده — چه آزمایش
خودکار، چه تعویض دستی خود مشتری — روی همان بلوک ثبت می‌شود. وقتی شمار مشاهده‌های منفی از
آستانه بگذرد، بلوک «سوخته» علامت می‌خورد و سرور تازه‌ای که رویش بیفتد، بدون اتلاف وقت
برای آزمایش، فوراً آدرسش عوض می‌شود. یک مشاهده مثبت، علامت را برمی‌دارد.

وضعیت این حافظه در `/admin/ip-health` دیده می‌شود: بلوک‌های سوخته، نرخ موفقیت هر لوکیشن و
ابزار آزمایش دستی یک آدرس. مدیر می‌تواند بلوکی را دستی سوخته یا سالم اعلام کند؛ تصمیم
دستی روی آمار خودکار اولویت دارد.

نرخ موفقیت هر لوکیشن، پس از جمع شدن دست‌کم ده مشاهده، در ویزارد ساخت سرور هم به مشتری
نشان داده می‌شود. این عددی است که هیچ رقیبی ندارد، چون داده‌اش را ندارد.

### لایه ۳ — پنجره تعویض رایگان

فیلترینگ روزبه‌روز عوض می‌شود و آدرسی که ظهر باز بوده ممکن است شب بسته شود. به همین دلیل
تا چند ساعت پس از ساخت سرور (پیش‌فرض ۴۸ ساعت)، تعویض آدرس رایگان است و از سهمیه ماهانه
هم کم نمی‌کند.

### تنظیمات

| کلید | پیش‌فرض | معنی |
| --- | --- | --- |
| `ipProbeEnabled` | روشن | بررسی خودکار آدرس‌ها |
| `ipProbePort` | ۲۲ | پورتی که آزمایش می‌شود |
| `ipProbeTimeoutMs` | ۶۰۰۰ | مهلت هر تلاش اتصال |
| `ipProbeTries` | ۳ | تلاش در هر دور؛ یک پاسخ موفق کافی است |
| `ipProbeRoundsToFail` | ۲ | دور ناموفق تا حکم «مسدود» |
| `ipAutoSwapEnabled` | روشن | تعویض خودکار آدرس مسدود |
| `ipAutoSwapMax` | ۲ | سقف تعویض خودکار هر سرور |
| `ipPrefixBadThreshold` | ۳ | مشاهده منفی تا سوختن یک بلوک /24 |
| `ipChangeFreeHours` | ۴۸ | پنجره تعویض رایگان پس از ساخت |

کار پس‌زمینه `verify-ip-reachability` هر دو دقیقه اجرا می‌شود و سرورهای شش ساعت گذشته را
که هنوز بررسی نشده‌اند رسیدگی می‌کند. اگر ورکر اجرا نشود، هیچ آدرسی بررسی نمی‌شود.

## تعویض آی‌پی سرور

در ایران آدرس سرورهای خارج زود از دسترس خارج می‌شود. کاربر می‌تواند از تب **تعویض آی‌پی**
در صفحه سرور، یک آدرس IPv4 کاملاً تازه بگیرد.

### تنظیمات

در `/admin/settings` بخش «تعویض آی‌پی سرور»:

| کلید | پیش‌فرض | معنی |
| --- | --- | --- |
| `ipChangeEnabled` | روشن | نمایش یا پنهان کردن این امکان برای همه کاربران |
| `ipChangeFee` | ۱۵۰٬۰۰۰ تومان | مبلغی که پیش از شروع از کیف پول کسر می‌شود |
| `ipChangeMaxPerMonth` | ۳ | سقف دفعات موفق در هر ماه برای هر سرور (صفر یعنی بی‌نهایت) |
| `ipChangeFreeHours` | ۴۸ | تا این ساعت پس از ساخت، تعویض رایگان است و سهمیه مصرف نمی‌کند |

مبلغ را کمتر از هزینه واقعی Primary IP در هتزنر تعیین نکنید.

### مراحل اجرا

1. بررسی شرایط: فعال بودن امکان، نبودن درخواست در جریان، سقف ماهانه و وضعیت سرور.
2. کسر هزینه از کیف پول و ثبت رکورد در جدول `server_ip_changes`.
3. رزرو یک Primary IP تازه در همان دیتاسنتر سرور.
4. خاموش کردن سرور و انتظار تا وضعیت `off`.
5. جدا کردن آدرس قبلی و اتصال آدرس جدید.
6. روشن کردن سرور و آزاد کردن آدرس قبلی.
7. به‌روزرسانی آدرس در پنل، صفر کردن پایش و ارسال اعلان به کاربر.

آدرس قدیمی پس از تعویض **به‌طور قطعی از حساب هتزنر حذف می‌شود** تا هزینه ماهانه‌ای
نسازد؛ حذف چند بار تلاش می‌شود و اگر باز هم نشد، جاروب ساعتی «آدرس‌های بلااستفاده» بعداً
پاکش می‌کند و به تیم هم خبر می‌دهد. همین جاروب آدرس‌های جامانده از سرورهای حذف‌شده را هم
در همه حساب‌ها پیدا و حذف می‌کند و از `/admin/ip-health` به صورت دستی هم قابل اجراست.
آدرس‌های جوان‌تر از نیم ساعت دست نمی‌خورند تا با عملیات در جریان تداخلی پیش نیاید.

مدت قطعی معمولاً یک تا سه دقیقه است. اگر هر مرحله شکست بخورد، پنل آدرس قبلی را برمی‌گرداند،
آدرس تازه را حذف می‌کند، سرور را دوباره روشن می‌کند و **کل مبلغ را به کیف پول برمی‌گرداند**؛
آن تلاش سهمیه ماهانه را هم مصرف نمی‌کند.

> آدرس قبلی برای همیشه آزاد می‌شود و برگشت‌پذیر نیست. رکوردهای DNS، فایروال‌های بیرونی و
> لایسنس‌هایی که به آدرس قبلی بسته شده‌اند باید به‌روزرسانی شوند.

## نسخه موبایل و تم

### موبایل

- نوار پیمایش پایین صفحه با چهار میان‌بر پرکاربرد و دکمه «بیشتر» برای منوی کامل.
- جدول‌ها زیر ۷۶۸ پیکسل به کارت تبدیل می‌شوند؛ عنوان هر سلول از `data-label` خوانده می‌شود
  و اسکرول افقی از بین می‌رود.
- فهرست سرورها و انتخاب پلن در ویزارد ساخت، روی گوشی نمای کارتی اختصاصی دارند.
- مودال‌ها روی گوشی به شکل شیت از پایین باز می‌شوند و دکمه‌هایشان تمام‌عرض است.
- اندازه لمس‌پذیر دکمه‌ها دست‌کم ۴۴ پیکسل و اندازه فونت ورودی‌ها ۱۶ پیکسل است تا سافاری
  هنگام تایپ صفحه را زوم نکند.
- `env(safe-area-inset-*)` رعایت شده تا روی گوشی‌های دارای ناچ چیزی زیر لبه نرود.
- فایل `manifest.webmanifest` اضافه شده؛ کاربر می‌تواند پنل را روی صفحه اصلی گوشی نصب کند
  و بدون نوار آدرس، مثل اپلیکیشن بازش کند.

### تم روشن و تیره

سه حالت دارد و انتخاب کاربر در `localStorage` با کلید `pm-theme` می‌ماند:

| حالت | رفتار |
| --- | --- |
| خودکار (پیش‌فرض) | از تنظیمات سیستم‌عامل یا گوشی پیروی می‌کند و تغییر آن را زنده دنبال می‌کند |
| روشن | همیشه روشن |
| تیره | همیشه تیره |

تغییر تم از دکمه بالای نوار (در همه صفحه‌ها) یا از کارت «ظاهر پنل» در صفحه حساب کاربری
انجام می‌شود. یک اسکریپت کوچک پیش از نخستین رنگ‌آمیزی اجرا می‌شود تا صفحه با تم درست بالا
بیاید و کاربر پرش سفید به تیره نبیند. رنگ نوار وضعیت مرورگر موبایل هم با تم هماهنگ می‌شود.

## ابزارهای رشد و فروش

### صفحه عمومی فروش

بازدیدکننده بدون ورود، در نشانی اصلی سایت صفحه فروش کامل می‌بیند: قیمت زنده پلن‌ها (که با
نرخ روز یورو حساب می‌شود)، لوکیشن‌ها به همراه درصد واقعی دسترسی از ایران (وقتی نمونه کافی
جمع شده باشد)، امکانات، پرسش‌های پرتکرار و دکمه ثبت‌نام. کاربر واردشده مستقیم به داشبورد
می‌رود.

### کد هدیه و کد شارژ بیشتر

از `/admin/promos` دو نوع کد می‌سازید:

| نوع | رفتار |
| --- | --- |
| هدیه مستقیم | کاربر کد را در کیف پول وارد می‌کند و مبلغ فوراً شارژ می‌شود |
| شارژ بیشتر | کاربر کد را هنگام شارژ می‌زند و پس از پرداخت موفق، درصدی اضافه هدیه می‌گیرد |

سقف کل استفاده، سقف هر کاربر، حداقل مبلغ شارژ، سقف مبلغ هدیه، «فقط شارژ اول» و تاریخ
انقضا قابل تنظیم است. مصرف هر کد و مجموع مبلغ هدیه‌شده در همان صفحه دیده می‌شود. کد
استفاده‌شده برای حفظ سابقه مالی حذف نمی‌شود و فقط غیرفعال می‌گردد. مصرف کد اتمی است و
با استفاده همزمان، از ظرفیت بیشتر خرج نمی‌شود.

### باشگاه مشتریان

تخفیف پلکانی خودکار بر اساس مجموع مصرف واقعی (کسر بابت سرویس منهای بازگشتی‌ها):

| سطح | آستانه پیش‌فرض | تخفیف پیش‌فرض |
| --- | --- | --- |
| 🥉 برنزی | — | ۰٪ |
| 🥈 نقره‌ای | ۵ میلیون تومان | ۲٪ |
| 🥇 طلایی | ۲۰ میلیون تومان | ۴٪ |
| 💎 الماس | ۶۰ میلیون تومان | ۶٪ |

آستانه‌ها و درصدها در تنظیمات قابل تغییرند. سطح کاربر هرگز پایین نمی‌آید و تخفیف مؤثر او
بیشترینِ تخفیف دستی مدیر و تخفیف سطح است که خودکار در کاتالوگ، پیش‌فاکتور، ساخت و
ارتقا اعمال می‌شود. سطح‌ها روزانه و پس از هر خرید بازمحاسبه می‌شوند و ارتقا با ایمیل و
اعلان تبریک همراه است. کاربر پیشرفتش را با نوار پیشرفت روی داشبورد می‌بیند.

### گزارش هفتگی ایمیلی

جمعه‌ها برای هر کاربر دارای سرور: هزینه و شارژ هفته، ترافیک مصرفی، وضعیت سرورها و
پایش‌ها، موجودی و برآورد دوامش. اگر موجودی برای کمتر از سه روز کافی باشد، دکمه شارژ
برجسته می‌شود. کاربر می‌تواند از بخش اطلاع‌رسانی خاموشش کند و مدیر هم کلید سراسری دارد.

## نرخ خودکار یورو

نرخ آزاد یورو مبنای همه قیمت‌هاست و به‌روزرسانی دستی‌اش هم فراموش می‌شود و هم دیر.
پنل می‌تواند نرخ را خودش از منبع انتخابی شما بگیرد، حاشیه دلخواهتان را رویش بکشد و در
بازه قابل تنظیم اعمال کند. پیکربندی در `/admin/pricing`، کارت «نرخ خودکار یورو».

### منابع

| منبع | توضیح |
| --- | --- |
| نوسان (navasan.tech) | نیازمند کلید API رایگان؛ نرخ را به تومان می‌دهد |
| tgju.org | بدون کلید؛ نرخ ریالی است و خودکار تقسیم بر ده می‌شود |
| دلخواه | هر آدرس JSON با مسیر مقدار (مثل `eur.value`) و واحد تومان یا ریال |

دکمه «آزمایش دریافت» بدون اعمال، نشان می‌دهد منبع چه عددی می‌دهد و پس از حاشیه چه
می‌شود؛ پیش از روشن کردن حالت خودکار، همین را بزنید تا از درستی پیکربندی مطمئن شوید.

### فرمول

```
نرخ نهایی = گرد( نرخ منبع × (۱ + حاشیه درصدی) + حاشیه ثابت )
```

### محافظ‌ها

یک عدد غلط می‌تواند قیمت همه پلن‌ها را خراب کند، پس:

- نرخ خارج از بازه منطقی (کمتر از ۵ هزار یا بیشتر از ۲۰ میلیون تومان) هرگز پذیرفته نمی‌شود.
- اگر نرخ تازه بیش از «سقف تغییر» (پیش‌فرض ۱۰٪) با نرخ فعلی فرق داشته باشد، اعمال نمی‌شود
  و به مدیر ایمیل و اعلان می‌رسد تا دستی تصمیم بگیرد.
- سه شکست پیاپی در دریافت، هشدار می‌سازد تا قیمت‌ها روی نرخ کهنه نمانند.
- هر دریافت — موفق یا رد شده — در تاریخچه ثبت و در همان کارت نمایش داده می‌شود.

کار پس‌زمینه هر ۳۰ دقیقه بیدار می‌شود ولی فقط وقتی «بازه به‌روزرسانی» شما گذشته باشد نرخ
تازه می‌گیرد. چون قیمت‌ها همیشه از نرخ لحظه‌ای حساب می‌شوند، به محض اعمال نرخ تازه همه
قیمت‌های کاتالوگ و ویزارد ساخت هم عوض می‌شوند.

## ایمیل، پیامک و همگام‌سازی خودکار کاتالوگ

**سرور ایمیل از داخل پنل.** در «ایمیل و پیامک» (`/admin/messaging`) میزبان، پورت، نام
کاربری و رمز SMTP را وارد کنید؛ رمز با AES-256 رمزنگاری می‌شود و بر مقادیر `.env`
اولویت دارد. همان‌جا دکمه «آزمایش اتصال»، ارسال ایمیل و پیامک آزمایشی، آمار ۳۰ روزه و
لاگ کامل ایمیل‌های ارسالی (گیرنده، موضوع، نتیجه، علت شکست) را دارید. لاگ‌های
قدیمی‌تر از ۹۰ روز خودکار پاک می‌شوند. پیکربندی پیامک همچنان در `.env` است
(`SMS_API_KEY`) ولی آزمایش ارسالش از همین صفحه انجام می‌شود.

**کاتالوگ خودکار.** کار پس‌زمینه `catalog-auto-sync` هر ساعت اجرا می‌شود و اگر طبق بازه
تنظیم‌شده وقتش شده باشد، پلن‌ها، لوکیشن‌ها و مهم‌تر از همه «موجودی هر پلن در هر
دیتاسنتر» را از هتزنر تازه می‌کند؛ پس اگر پلنی در هتزنر تمام یا موجود شود، سایت
خودکار همان را نشان می‌دهد. کلید روشن/خاموش و بازه (پیش‌فرض ۱ ساعت) بالای صفحه
کاتالوگ است. پلن‌ها و لوکیشن‌هایی که خودتان خاموش کرده‌اید با همگام‌سازی دست نمی‌خورند.

## نحوه کار موتور قیمت‌گذاری

```
قیمت هتزنر (یورو، با VAT)
  × نرخ یورو به تومان
  × (۱ + درصد سود ÷ ۱۰۰)
  × (۱ − تخفیف کاربر ÷ ۱۰۰)
  × (۱ + مالیات ÷ ۱۰۰)
  + مبلغ ثابت
  → گرد شدن به بالا
```

قوانین قیمت‌گذاری به ترتیب اولویت اعمال می‌شوند و **اولین قانون منطبق برنده است**:

```
کاربر مشخص  ←  پلن مشخص  ←  لوکیشن مشخص  ←  سراسری
```

تمام مبالغ به صورت **عدد صحیح تومان** (`BigInt`) ذخیره می‌شوند؛ هیچ‌جا از اعداد اعشاری برای پول استفاده نمی‌شود.

## نحوه کار موتور صورتحساب

### سرور ساعتی

- هنگام ساخت، هزینه یک ساعت بلافاصله کسر می‌شود.
- کاربر باید حداقل معادل `hourlyPrepayHours` ساعت (پیش‌فرض ۲۴) اعتبار داشته باشد.
- هر ساعت، ورکر هزینه ساعت‌های سپری‌شده را کسر می‌کند.
- **سقف ماهانه:** مجموع کسر هر ماه هرگز از قیمت ماهانه بیشتر نمی‌شود (همان قاعده هتزنر).
- خاموش کردن سرور هزینه را متوقف نمی‌کند؛ فقط حذف سرور آن را متوقف می‌کند.

### سرور ماهانه

- هزینه کل دوره (۱ تا ۱۲ ماه) در ابتدا کسر می‌شود.
- در سررسید، اگر تمدید خودکار فعال باشد فاکتور صادر و از کیف پول پرداخت می‌شود.
- اگر غیرفعال باشد، سرور در سررسید تعلیق می‌شود.

### چرخه تعلیق و حذف

```
موجودی تمام شد
   ↓  (اعلان فوری + ایمیل)
مهلت suspendGraceHours ساعت (پیش‌فرض ۶)
   ↓
تعلیق: سرور خاموش می‌شود، داده‌ها باقی می‌مانند
   ↓  (کاربر هر لحظه شارژ کند، خودکار روشن می‌شود)
پس از deleteAfterDays روز (پیش‌فرض ۷)
   ↓
حذف کامل و غیرقابل بازگشت
```

### ضمانت‌های مالی

- هزینه **قبل** از ساخت سرور کسر می‌شود؛ اگر ساخت شکست بخورد، وجه کامل برمی‌گردد و سرور نیمه‌ساخته از هتزنر حذف می‌شود.
- تمام تغییرات موجودی داخل تراکنش دیتابیس و از طریق ماژول `wallet` انجام می‌شود، پس دفتر تراکنش‌ها همیشه با موجودی هم‌خوان است.
- تایید دوباره یک پرداخت (بازپخش callback) هرگز باعث شارژ مضاعف نمی‌شود.

## اطلاع‌رسانی و ربات تلگرام

### آستانه هشدار اعتبار

هر کاربر خودش تعیین می‌کند **چند ساعت قبل از اتمام اعتبار** خبردار شود. سامانه مصرف واقعی سرورهای او را حساب می‌کند، نه یک مبلغ ثابت:

```
ساعت باقی‌مانده = موجودی ÷ مصرف ساعتی
اگر ساعت باقی‌مانده ≤ آستانه کاربر  →  هشدار
```

پیش‌فرض ۴۸ ساعت است و در `/admin/settings` قابل تغییر است. کاربر می‌تواند بین ۱۲ ساعت تا ۳۰ روز انتخاب کند یا مقدار دلخواه بگذارد. یک آستانه مبلغی هم به عنوان شرط دوم قابل تنظیم است.

هرچه به اتمام نزدیک‌تر شویم، یادآوری‌ها فشرده‌تر می‌شوند: بالای ۲۴ ساعت روزی یک بار، زیر ۲۴ ساعت هر ۸ ساعت و زیر ۶ ساعت هر ۳ ساعت.

### کانال‌ها و دسته‌بندی

کاربر برای هر کانال (ایمیل، تلگرام، پیامک) و هر دسته رویداد (سرور، مالی، پشتیبانی، قطعی، اطلاعیه) جداگانه تصمیم می‌گیرد. اعلان‌ها همیشه داخل پنل ثبت می‌شوند؛ این تنظیمات فقط کانال‌های بیرونی را کنترل می‌کنند.

رویدادهای امنیتی حساب همیشه ارسال می‌شوند و قابل خاموش کردن نیستند.

### ساعات سکوت

کاربر می‌تواند بازه‌ای تعریف کند که در آن پیام بیرونی نگیرد. هشدارهای فوری (قطعی سرور، اتمام اعتبار زیر ۱۲ ساعت، رویدادهای امنیتی) از این قاعده مستثنا هستند.

### سقف بودجه ماهانه

کاربر یک سقف هزینه تعیین می‌کند و در درصد مشخصی از آن هشدار می‌گیرد. این فقط هشدار است و سرویسی را قطع نمی‌کند.

### ربات تلگرام

راه‌اندازی کامل در [docs/ربات-تلگرام.md](docs/ربات-تلگرام.md) توضیح داده شده. خلاصه:

```bash
# ۱. از @BotFather توکن بگیرید و در .env بگذارید
TELEGRAM_BOT_TOKEN=...

# ۲. بررسی اتصال و دریافت فهرست دستورها
npm run telegram

# ۳. ورکر را اجرا کنید (پیام‌ها را با long polling می‌گیرد)
npm run worker
```

اگر سرور شما به `api.telegram.org` دسترسی مستقیم ندارد، آدرس پروکسی را در `TELEGRAM_API_URL` بگذارید.

## پایش سرور

وضعیتی که هتزنر گزارش می‌دهد فقط می‌گوید ماشین مجازی روشن است. پایش پنل از **بیرون** به سرویس واقعی مشتری وصل می‌شود، پس اگر سیستم‌عامل هنگ کند یا وب‌سرور بالا نیاید هم متوجه می‌شود.

| ویژگی | جزئیات |
|---|---|
| نوع بررسی | اتصال TCP، درخواست HTTP یا HTTPS |
| فاصله | ۱ تا ۶۰ دقیقه، به انتخاب کاربر |
| آستانه هشدار | پس از چند خطای پیاپی هشدار داده شود (پیش‌فرض ۲) |
| گزارش | درصد آپ‌تایم ۳۰ روز، میانگین زمان پاسخ، نوار روزانه و تاریخچه قطعی |

هنگام ساخت سرور، پایش به‌طور خودکار فعال می‌شود: برای قالب‌های وب روی پورت ۸۰ و در بقیه موارد روی پورت ۲۲.

برای اینکه بار شبکه کنترل شود، بررسی‌ها دسته‌ای (۲۵تایی موازی) انجام می‌شوند و فقط سرورهایی که نوبتشان رسیده بررسی می‌گردند.

## عیب‌یابی

**کاتالوگ خالی است / پلنی نمایش داده نمی‌شود**
`HETZNER_API_TOKEN` را بررسی کنید و در `/admin/catalog` همگام‌سازی را اجرا کنید.

**هزینه‌ای از کاربران کسر نمی‌شود**
ورکر اجرا نشده است. با `npm run worker` اجرا کنید یا در `/admin` بخش «سلامت سیستم» زمان آخرین اجرای کارها را ببینید.

**پرداخت انجام شد ولی کیف پول شارژ نشد**
به `/admin/transactions` بروید، تراکنش را با فیلتر «در انتظار» پیدا کنید و روی «بررسی» و سپس «استعلام مجدد از درگاه» بزنید.

**ساخت سرور با خطای «ظرفیت خالی وجود ندارد»**
هتزنر در آن لوکیشن موجودی ندارد. لوکیشن دیگری انتخاب کنید یا آن پلن را موقتاً از `/admin/catalog` غیرفعال کنید.

**ایمیل ارسال نمی‌شود**
بدون `SMTP_HOST` ایمیل‌ها فقط در کنسول چاپ می‌شوند. مقادیر SMTP را تنظیم و سرویس را دوباره راه‌اندازی کنید.

**اعلان «سرور بدون مالک در هتزنر»**
سروری در هتزنر هست که رکورد محلی ندارد. در کنسول هتزنر بررسی و در صورت لزوم حذفش کنید تا هزینه بیهوده ندهید.

**کاربر می‌گوید هشدار اعتبار نگرفت**
در پنل کاربر بخش اطلاع‌رسانی را ببینید: ممکن است هشدار را خاموش کرده باشد، آستانه‌اش خیلی کم باشد یا ساعات سکوت فعال باشد. همچنین مطمئن شوید کار `low-balance-alerts` در ورکر اجرا می‌شود.

**ربات تلگرام پاسخ نمی‌دهد**
`npm run telegram` را اجرا کنید تا اتصال بررسی شود. جزئیات بیشتر در [docs/ربات-تلگرام.md](docs/ربات-تلگرام.md).

**پایش سرور هشدار اشتباه می‌دهد**
پورت بررسی را چک کنید. اگر فایروال ابری پورت ۲۲ را بسته باشد، پایش TCP آن را قطع گزارش می‌کند. پورت را به سرویسی که واقعاً باز است تغییر دهید.
